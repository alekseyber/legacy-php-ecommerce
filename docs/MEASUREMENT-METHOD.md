# Методика замера происхождения движка

Как измерялось, что в этом репозитории пришло из учебного каркаса, а что написано за
2011–2021 годы. Документ нужен, чтобы цифры из README можно было воспроизвести и
проверить, а не принимать на слово.

## Что с чем сравнивается

| роль | что именно | где берётся |
|---|---|---|
| база (отправная точка) | финальный проект учебного курса: `ishop2.loc` — `app/`, `vendor/ishop/core`, `config/`, `public/` | архив курса, урок 32 (`part3/32/3_32_files.rar`) |
| цель | финал этого репозитория, 24.10.2021 | корень репозитория |

**Брать именно финальный урок, а не первый.** В курсе каждый урок — самостоятельный архив;
первый урок содержит пустой каркас, и замер от него покажет «почти всё написано автором»,
что бессмысленно.

**Только эта линия.** Живой магазин на другом домене — ответвление и более старая
переработанная редакция; он не является ни базой, ни целью для этих чисел. Линия одна:
курс → winter-boots.

## Охват

Считается три слоя: `vendor/ishop` (ядро движка), `app` (контроллеры, модели, вьюхи,
виджеты), `config`.

**Что исключено и почему:**

- `vendor/` вне `vendor/ishop` — RedBean, SwiftMailer, Valitron, TCPDF, PhpSpreadsheet,
  GeoIP2: чужие библиотеки, к происхождению движка отношения не имеют;
- `public/` — 97 файлов из 102 там сторонние (kcfinder и подобное), они искажают результат
  в обе стороны;
- `frontend/`, `docker/`, `docs/` — появились при подготовке этого репозитория к публикации,
  а не в ходе разработки магазина.

## Команда

```bash
cd /opt/data/projects/code-evolution-diff
python3 compare.py \
  --baseline  /opt/data/tmp/base2/ishop2.loc \
  --target    /opt/data/projects/winter-boots-github \
  --layers    "vendor/ishop,app,config" \
  --threshold 0.30 --strong 0.60
```

`--layers` принимает **один** аргумент со списком через запятую; три отдельных аргумента
дают `unrecognized arguments`.

## Проверка, что цифры не врут

1. **Классы складываются в объём.** В каждом слое `как есть + переработано + ново = цель
   по строкам`, а число файлов в трёх колонках равно числу файлов цели. Если не сходится —
   прогон битый, а не «особенность».
2. **Итог равен сумме слоёв.** 738 + 4 141 + 35 697 = 40 576, файлы 20 + 60 + 248 = 328.
3. **Дословные совпадения обязаны совпадать между прогонами.** 49 (ядро) + 689 (приложение) =
   738 — ровно столько же, сколько в итоговой строке. Это признак того, что база и цель
   в прогонах одни и те же.

## Грабли

- **Проценты из разных прогонов нельзя ставить рядом.** Раньше в README стояло 87,2 %
  по всему дереву; оно считалось до появления `docker/`, `docs/`, `frontend/` и с исключённым
  `public`, поэтому со слоями не складывалось (расхождение 394 строки переработки и 241
  строка нового). Правило: все числа в документе — из одного прогона с одним охватом.
- **Фильтр слоёв меняет пул кандидатов и может сдвинуть класс.** `Router.php` и
  `ErrorHandler.php` в изолированном прогоне только по ядру давали 0,89 и 0,85 (сильные
  совпадения), а в общем прогоне по трём слоям уходят ниже 0,60 и попадают в
  «переработанные». Поэтому в README названы только те файлы, которые подтверждаются
  в согласованном прогоне.
- **Порог 0.30 ловит случайные совпадения коротких файлов.** Проценты отвечают на вопрос
  «сколько переписано», а «что перешло» показывают только сильные совпадения.
- **Совпадение 1.00 — это буквально одинаковый файл**, здесь оговорок нет. Всё остальное —
  сходство по содержимому после снятия комментариев; переписанное заново читается как
  «новое», скопированное с правкой namespace — как «переработанное».
- **Строки ≠ усилие.** 1,8 % дословного кода — это три файла ядра, то есть каркас, вокруг
  которого всё построено; по объёму они малы, по роли — нет.
