# Аудит запросов к базе перед публикацией

Проведён 20.11.2026 при подготовке архива к публикации. Цель — не доказать, что всё было хорошо, а не выпустить в открытый доступ пример с неэкранированными запросами.

## Что проверялось

459 вызовов SQL в `app/` и ядре `vendor/ishop`. Каждый разбор шёл по трём вопросам:

1. есть ли плейсхолдеры (`?`) и параметры — тогда подстановка безопасна по определению;
2. если запрос собирается строкой — что именно подставляется: константа, число, полученное из базы, или данные, пришедшие извне;
3. если данные извне — есть ли приведение к целому или экранирование.

## Результат

Всего найдено пять мест, где запрос собирался строкой с данными, и одно место, где подставлялось имя таблицы. После разбора по происхождению данных осталось три правки.

### 1. Имя таблицы из POST — исправлено

`app/controllers/admin/CsvController.php`, выгрузка таблицы в CSV.

Было: `SELECT * FROM $action`, где `$action = $_POST['action']`. Рядом стояла проверка `property_exists('Csv', $action)`, которая проверяет свойство у класса с именем «Csv» и поэтому всегда возвращала «нет» — то есть не защищала вообще.

Стало: имя сверяется с фактическим списком таблиц базы (`SHOW TABLES`) после проверки на допустимые символы. Единственное место, где возможна инъекция, — и то только из админки после авторизации.

### 1a. Обмен CSV ограничен таблицами каталога — исправлено

**Было.** Экспорт и импорт CSV принимали любое имя таблицы из POST. Проверка существования таблицы защищала от ошибки, но не от выбора: через `action=orders` админ выгружал имена, телефоны, адреса и IP клиентов, через `action=user` — логины и хеши паролей, а импортом в `user` можно было перезаписать строку пользователя, то есть подменить пароль или роль. В интерфейсе кнопки есть только у товаров и UTM, но запрос собирается руками за минуту.

**Стало.** Обмен разрешён только для таблиц каталога: `product`, `modification`, `modificationregistr`, `registr`, `category`, `brand`, `color`, `sizes`, `sizesgroup`, `attribute_group`, `attribute_value`, `attribute_product`, `page`, `news`, `citypage`, `utm`. Остальные — отказ с сообщением.

**Проверено на стенде:** `action=orders` и `action=user` дают редирект с ошибкой и пустое тело, `action=product` отдаёт CSV из 162 строк.

### 2. Имя файла в галерее — исправлено

`app/models/admin/Modification.php`, `saveGallery()`.

Было: `INSERT INTO gallery (img, modification_id) VALUES $sql_part`, где `$sql_part` собирался из имён файлов строкой.
Стало: по одной вставке на файл с плейсхолдерами.

### 3. Состав заказа — исправлено

`app/models/Order.php`, сохранение позиций заказа.

Было: значения для `INSERT INTO orderproduct ... VALUES` собирались строкой из элементов корзины. Данные берутся из базы, поэтому удалённой инъекции здесь не было, но товар с апострофом в названии ломал оформление заказа — то есть это ошибка устойчивости, а не безопасности.
Стало: плейсхолдеры, число строк собирается отдельно.

### 4. Приведение к целому — добавлено

`app/controllers/AppController.php`, `requestChekTable()`: параметр приводится к `int` перед подстановкой в запрос. Риск был низкий (передаются внутренние константы), правка ради аккуратности.

### 5. Оставлено без изменений — проверено

`app/models/admin/Sizesgroup.php` и `app/models/admin/Product.php` собирают `VALUES` строкой, но каждое значение предварительно приводится к `int`. Инъекция невозможна, поведение не меняется — править не стал, чтобы не переписывать работающую бизнес-логику без необходимости.

**Безопасно по построению:** виджет фильтра (`$sql_part` строится из `id`, полученных из базы, и имён таблиц из конфига), поисковый индекс (`app/models/Api.php`), выборка параметров страницы. Внешне они выглядят опаснее всего, потому что подставляют много переменных, но источник данных закрыт базой и конфигурацией.

## Граница доверия — что этот аудит говорит о подходе

Код последовательно аккуратен на публичной границе: в корзину из запроса попадают только `pid`, `product_model`, `nosizeselect` и `edit`, все приводятся к `int`, а данные товара выбираются запросом с плейсхолдерами. За границей авторизации аккуратность ниже: там подразумевалось, что владелец не станет ломать собственный магазин.

Это рационально ровно до момента, когда появляется второй человек с доступом, утекает сессия администратора или у системы появляется внешний потребитель. Поэтому правки сделаны не «потому что через них ломали», а потому что граница доверия — это инженерное решение, и её надо называть явно, а не оставлять в голове автора.

## Отдельная находка: заказ подтверждался при сбое транзакции

Не про SQL-инъекции, но найдено тем же проходом и опаснее по последствиям.

`Order::saveOrder()` выполняет работу в транзакции: `R::begin()` → вставка заказа → вставка позиций → `R::commit()`. В `catch` был `R::rollback()` — и сразу после блока, уже вне `try`, стоял безусловный `return true`. Контроллер (`CartController::orderAction`) вызывал `saveOrder()`, не проверяя результат, затем `mailOrder()` и строил страницу подтверждения.

Что получалось при любом сбое вставки (апостроф в названии товара, нехватка места, разрыв соединения):

- в базе заказа нет (откат сработал);
- клиент видит «Заказ №N получен, спасибо»;
- админ получает письмо «Сделан заказ №N»;
- корзина очищается, и клиент теряет набранное.

Исправлено: `saveOrder()` при сбое пишет ошибку в `tmp/errors.log` и возвращает `false`; контроллер при `false` не отправляет письмо, не чистит корзину и не показывает подтверждение. В шаблон корзины добавлен вывод ошибки.

### Что проверено на стенде

Сбой имитировался принудительным исключением внутри транзакции:

| проверка | до правки | после |
|---|---|---|
| заказов в базе | 131 → 131 (не создан) | 131 → 131 (не создан) |
| писем админу | 2 → 3 (письмо о несуществующем заказе) | 2 → 2 (письма нет) |
| корзина после сбоя | очищалась | сохранена |
| запись в `tmp/errors.log` | нет | есть, с текстом ошибки |
| успешный заказ после снятия имитации | — | создан (132-й, №1227-67), позиция записана, письмо ушло, редирект на `/cart/orderdone` |

Оговорка: видимость сообщения об ошибке в браузере проверить не удалось — в архиве нет основного слоя JS (он был в `.gitignore`), а именно он выводит ответы формы. В серверном (не-JS) пути блок вывода ошибки добавлен, но на стенде он не отрисовывается, потому что страница опрашивается скриптом. Утверждать «клиент увидит сообщение» на основании стенда нельзя; утверждать «заказ не будет подтверждён ложно и письмо не уйдёт» — можно, это проверено по базе, почте и логу.

## Проверка

Синтаксис изменённых файлов проверен интерпретатором PHP 7.0 (`php -l`) — ошибок нет.
